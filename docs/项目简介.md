# AI 图片生成器（个人项目 · 简历版）

> 一句话：一句自然语言描述 → 提示词优化 → 智谱文生图 → 本地素材库持久化，同一份 React 渲染层同时跑在 Web 与 Electron 桌面端。

---

| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 角色     | 独立开发（渲染层 + BFF 代理 + Electron 桌面端）                                                                                                                                            |

## 二、系统架构

```
浏览器 / Electron 渲染层（共用同一份 src/）
   │  构建期 @platform 别名切换实现
   ├─ web/        /api 相对路径 → Pages Functions ─┐
   └─ desktop/    VITE_API_BASE → Pages Functions ─┤
                                                  ▼
                                            智谱 AI 开放平台
                                                 （cogview-3-plus / glm-4-flash）

Electron 主进程
   ├─ app:// 自定义协议    加载 dist（避免 file:// 下 IndexedDB 不可用）
   ├─ app://images/<id>    提供本地图片副本
   ├─ history.json + images/   历史记录与图片落盘
   └─ net.fetch            抓取外链图片（不受浏览器 CORS 限制）
```

平台差异被收敛成 4 个入口：`historyStore`（历史与图片副本）、`directImageSrc` / `resolveImageSrc`（引用解析）、`saveImage`（保存文件）、`target`（运行端标识）。业务代码只依赖 `src/services/platform.ts` 中的契约，不感知运行环境。

## 三、核心工作

1. **密钥隔离的 BFF 代理**：把智谱 Key 放在 Cloudflare Pages Functions 的 Secret 中，前端只调同源 `/api/*`；代理层做参数白名单（尺寸仅允许 `1024x1024 / 768x1344 / 1344x768`）、上游错误归一化（401/429 → 可读中文提示），并把"风格"拼装进最终提示词。明确拒绝 `VITE_` 前缀存放密钥（会被打进前端产物）。

2. **一套代码双端交付**：抽出 `PlatformApi` 契约，`vite.config.ts` 按 `--mode desktop` 把 `@platform` 指向 `src/platform/desktop`，`tsconfig` 用 `paths` 指向 web 实现保证两边签名一致；产物分别为 `base: "/"`（Web）与 `base: "./"`（桌面）。双端共用同一后端，桌面端只需一个 `VITE_API_BASE`。

3. **历史记录存储重构（localStorage → IndexedDB）**：原来是「元数据 + 远程图片 URL」塞进 5MB 的 localStorage，图片链接过期后历史全是裂图。改为 `meta`（元数据）+ `images`（Blob）双 store：生成成功后把临时链接抓成本地 Blob，加载时优先用本地副本；保留旧 key 的一次性迁移；容量上限从 5MB 提到数百 MB。

4. **修复首帧覆盖数据的隐性 Bug**：原代码「加载 effect」在前、「保存 effect」在后，首帧会用空数组写回存储——localStorage 同步写入时被下一次渲染侥幸覆盖回来，一旦改成异步 IndexedDB 就会真实丢历史。改为 `isHydrated` 守卫，读取完成前不写回。

5. **Electron 外壳**：主进程注册 `standard + secure + supportFetchAPI` 的 `app://` 协议承载构建产物；`contextIsolation + sandbox` 下通过 preload 暴露最小 API；单实例锁；`window.open` 一律转系统浏览器；下载改为原生保存对话框 + 主进程写盘。

6. **桌面端文件存储**：历史元数据落 `userData/history.json`（`.tmp` + `rename` 原子替换），图片副本落 `userData/images/<id>.png`，引用统一为 `app://images/<id>.png`；协议处理器按 host 分流并做路径穿越校验；保存时清理超过 10 分钟的孤儿图片；旧版桌面壳的 IndexedDB 数据在首次启动时一次性迁移到文件存储。

7. **把 CORS 问题下沉到主进程**：浏览器端抓取智谱 OSS 临时链接经常因缺少 CORS 头失败，桌面端改由主进程 `net.fetch` 抓取并落盘，顺带复用系统代理；渲染层仅做兜底，保证两端行为一致但能力递进。

## 四、关键难点与解法

**1. 远程图片链接会过期**

智谱返回的是临时 URL，直接入库必然失效。做法分三层：生成后立即尝试转存为本地副本；加载时若本地有副本则优先使用；确实抓不下来（跨域/过期）时继续按外链渲染并允许降级直链下载，不阻断主流程。

**2. Electron 用 `file://` 加载产物会整体失效**

`file://` 属于不透明来源，Chromium 不提供 IndexedDB，历史记录直接不可用；同时 Vite 默认 `base: "/"`，绝对路径资源在 `file://` 下解析失败导致白屏。解法是自定义 `app://` 协议 + 显式 MIME + 路径穿越校验，桌面构建改相对 `base`。

**3. 自定义协议的跨域可达性**

`app://` 作为 Origin 请求 Pages Functions 需要服务端放行。实测 `POST /api/optimize`（空 prompt）返回 400 + 业务错误体，证明预检与响应头（`Access-Control-Allow-Origin: *`）均正常，而非网络层失败。

**4. 双端存储能力不对等**

Web 只有 IndexedDB，桌面端可以真正落盘并调用系统能力。通过契约 + 别名注入实现"同一份 UI、不同实现"：web 实现基于 IndexedDB，desktop 实现基于文件系统 + IPC，缺失 preload 时自动回退 web 实现，保证用 desktop 构建在浏览器里也能调试。

**5. 冷启动延迟**

首次从桌面端请求线上函数耗时 52s，第二次 2.5s，同期 `curl` 约 5s——属于 DNS/TLS 与链路冷启动，不是应用层问题；定位方式是直接比对不同发起方的耗时，避免误改代码。

## 六、简历精简版（3 条）

- 独立开发 AI 图片生成应用（React 18 + TypeScript + Vite + Cloudflare Pages Functions + Electron），实现提示词优化、尺寸/风格参数、瀑布流历史与图片下载，服务端代理隔离大模型密钥。
- 抽象 `PlatformApi` 契约并以构建期别名注入，实现"一套渲染层双端交付"：Web 走同源 `/api`，Electron 走 `VITE_API_BASE`；桌面端以 `app://` 自定义协议加载产物，解决 `file://` 下 IndexedDB 不可用与绝对路径资源失效问题。
- 将历史记录从 localStorage 重构为「IndexedDB（Web）/ 文件系统（桌面）」双实现：图片转存本地 Blob 规避临时链接过期，桌面端用 `history.json` 原子写 + `images/<id>.png` + 主进程 `net.fetch` 抓图绕开 CORS，并修复首帧空数组覆盖历史的数据丢失隐患。

## 七、面试追问预案

| 追问                                | 回答要点                                                                                           |
| ----------------------------------- | -------------------------------------------------------------------------------------------------- |
| 为什么选 Electron 而不是 Tauri？    | 现有栈是纯 JS，Electron 接入成本最低且主进程能直接做文件与网络；Tauri 体积更优但需引入 Rust 工具链 |
| 为什么不用 `file://` 加载前端产物？ | 该来源下 Chromium 不提供 IndexedDB，且绝对路径资源会 404；改用 `app://`（standard + secure）       |
| 为什么不把 API Key 放桌面端？       | 客户端无法真正保密；统一由 Pages Functions 持有 Secret，桌面端只传业务参数                         |
| 双端怎么避免维护两套代码？          | 差异收敛到 4 个接口，构建期别名切换；契约用 TS interface 约束，两边实现都被类型检查                |
| 图片链接过期怎么处理？              | 生成后立即本地化 + 加载时优先本地副本 + 失败保留外链并允许直链下载，三层降级                       |
| 桌面端为什么不直接用 IndexedDB？    | 可以做，但不符合桌面应用预期：无法多端共享、清理缓存即丢、不便于用户管理；文件存储可迁移可备份     |

## 八、诚实边界

- 个人项目：单用户、无鉴权、无并发控制，历史仅存本地，无云同步。
- 桌面端未做打包分发：没有 `electron-builder`、代码签名/公证与自动更新，目前以开发模式或本地 `electron .` 运行。
- 未编写自动化测试，验证依赖双模式构建与手工/CDP 冒烟，未做压测。
- 无任务队列：生成是同步请求（10–30s），关窗即中断，没有断点续跑与系统通知。
- 生成质量取决于所选模型；错误提示依赖上游返回，429 常见于余额或资源包不足。
